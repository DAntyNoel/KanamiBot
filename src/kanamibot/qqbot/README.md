# 官方 QQBot 图库接入

## 独立 worktree 运行

主目录 `D:\DAntyNoel\kanami.top\KanamiBot` 保持 `dev`，
`feature/qqbot` 位于旁边的 `KanamiBot-qqbot` worktree。
这是独立的 NoneBot + 官方 QQ 适配器实例，不是新的 NapCat/OneBot 登录端。

在 feature worktree 中运行 `powershell -File scripts/start-qqbot.ps1`，
默认正式环境、仅监听 `127.0.0.1:12766`；测试沙箱追加 `-Sandbox`。
复用主目录 Python 依赖环境，不修改或重装该环境；进程的 `PYTHONPATH`
强制指向 feature 的 `src`，避免 editable 安装误加载 `dev` 的插件。
启动脚本不停止已有进程，端口占用会直接报错。日志保留在 feature 的 `logs/`。
同一个官方机器人不能让旧入口和新入口重复连接，应先确认并停止旧 QQBot 实例；
不要停止主目录的 OneBot Bot 或旧仓库服务。

本机使用 Windows Junction（不复制内容）：

- `KanamiBot-qqbot/data` → `KanamiBot/data`，共享图库及运行数据。
- `KanamiBot-qqbot/assets` → `KanamiBot/files`，复用当前实际素材目录；
  主仓库目前没有独立的 `assets` 目录。

链接仅用于本机，不提交；克隆到其他机器后需重新创建对应目录链接。
主目录 `dev` 尚未加载 feature 的图库锁，因此保持 QQBot 图库写入关闭，
不应为测试图片发送而开启 `enable_writes`。图片发送和公开图库读取不受影响。

`qq_sandbox.py` 与 `bot.py` 加载同一个 `plugins/image` 插件，共享
`data/advanced_media`，不复制图库。文件夹别名、哈希去重、可见性、预览编号、
负数索引、标签模糊检索和管理员权限使用同一套处理逻辑。

## 指令

群里发送 `@机器人 指令`，开启接收所有消息后可省略艾特。
QQBot 同样支持裸指令、`#` 和 `/` 前缀。

| 用途 | 指令及别名 |
| --- | --- |
| 保存 | `保存 <图库> [标签...]`，别名 `存图`、`收图`、`save_image` |
| 随机 | `随机 <图库>`，别名 `来点`、`pick_image` |
| 预览 | `所有 <图库>`，别名 `list_image`，管理员限定 |
| 检索 | `发送 <图库> <序号或标签>`，别名 `发`、`选择`、`select_image` |
| 信息 | 回复机器人发出的图库图片，发送 `信息`、`info`、`image_info` |
| 删除 | 回复图库图片，发送 `删除`、`移除`、`remove_image`、`delete_image`，管理员限定 |
| 加标签 | 回复图库图片，发送 `标签 <标签...>`、`打标`、`TAG`、`tag`，管理员限定 |
| 清标签 | 回复图库图片，发送 `清空标签`、`清除tag`、`删除tag`、`untag`，管理员限定 |

新图库只能由首个超管创建。群主/管理员可以维护已有图库，但不因此获得超管权限。
`image` 仍是收发测试指令，不是图库命令，且不自动回复普通图片消息。

## 首次升级与身份绑定

**必须先让所有共享图库的 Bot 都加载新版本，再开启 QQBot 写入。**
旧进程缓存整份元数据，不能与新写入端安全混用。新版本使用同一数据根目录的
跨进程锁，并在每次读写前重新读取元数据，避免丢记录和重复分配文件名。
损坏的元数据会阻止操作，不会被当成空图库覆盖。

1. 获得运行维护许可后，停止当前仓库的 `bot.py` 和 `qq_sandbox.py`。
   不操作 `D:\DAntyNoel\Kanami-NB` 的旧框架，也不重启 NapCat。
2. 更新代码，创建本地配置 `data/qqbot_gallery.json`（运行数据，不提交 Git）：

   ```json
   {
     "enable_writes": true,
     "group_bindings": {"已确认的群OpenID": 1125827968},
     "user_bindings": {"已确认的用户OpenID": 123456789},
     "superusers": ["已确认的首个超管用户OpenID"]
   }
   ```

3. 启动两个入口；真实邀请群使用 `qq_sandbox.py --production`。
   如还不知道 OpenID，可先不创建配置，启动 QQBot，在目标群发送 `图库身份`。
4. 管理员在本地确认并配置映射。**不能仅凭旧日志推断某个 OpenID 对应哪个群号。**
   配置每次指令读取，无需为了修改映射再次重启。

QQ 开放平台只提供 OpenID，不提供真实 QQ 号/群号。绑定后，原群私有图片、
贡献者信息、模块开关、黑名单和 `.env` 中的 QQ 超管身份可沿用。
`superusers` 也可直接指定官方用户 OpenID，第一个拥有建图库权限。
不要把 AppID 当作用户 OpenID，也不要把 AppSecret 写入此配置或发到群里。

未绑定身份使用独立负整数命名空间，不视为群号 `0`，不自动暴露其他群私有图片。
公开图库仍能读取；未绑定用户不会自动获得原 QQ 超管身份。
缺少配置或 `enable_writes` 不为 `true` 时，QQBot 仅开放读取，存图和维护会提示未启用。
身份绑定前若已产生私有数据，绑定后不会自动迁移其贡献群；应先绑定再开启写入。

## 官方接口的差异

- 支持当前消息附图和官方回复载荷里的附图；回复本 Bot 最近发送的图库图片也可存图。
  官方不提供 OneBot 的任意消息/合并转发读取接口，无法保证保存合并转发内容。
- 官方消息回执使用 `ext_info.ref_idx`，回复使用 `msg_idx`/`ref_msg_idx`；
  上下文按 Bot 和群隔离，保留 30 分钟、最多 1000 条，重启失效。
  不支持跨 Bot 引用另一机器人的内存记录。
- 官方不支持 OneBot 的成功贴表情和合并转发结果：成功存图改为文字确认，
  重复图用单张拼图展示输入图和已存图（最多 12 张），避免一次回复发送多图丢失。
- 单张接收图片最多 20 MB；实际发送仍受官方媒体审核、消息配额、回复时效及群设置限制。
  本地自动化测试不等于真实 QQ 客户端验收，需在目标群验证存图、发图和回复维护。

因此可统一日常命令和图库内容，但无法承诺平台能力、身份和消息展示完全无差别。
